# Tunnels & Nginx: известные грабли и их лечение

> Собранные по итогам реальных проблем: «ломаются стили без слеша на конце»,
> «VPN рвёт туннели», «зацикленные редиректы после смены домена».
> Все команды — через `dpx ddev <cmd> --here` из корня репо (правило START_HERE).

## 1. Обязательный слеш в конце URL (Nginx)

**Симптом:** страница открывается без `/` на конце (`/catalog/page-2`) —
редирект ведёт на внутренний адрес/порт, стили и картинки не грузятся, часть
запросов обрывается.

**Механика.** WordPress-ссылки каноничны **со слешем**. В Nginx запрос без
слеша обрабатывается `try_files $uri $uri/ /index.php?$args;`: если `$uri` не
файл, Nginx пробует `$uri/` как директорию — и при успехе отдаёт **301
redirect** на URI со слешем. По умолчанию (`absolute_redirect on`) Location
строится из `$host:$server_port` — то есть из ТОГО, что Nginx видит внутри:
локальный порт контейнера или внутреннее имя. За туннелем (Cloudflare/ngrok) и
обратным прокси этот внутренний адрес наружу не резолвится — браузер уходит в
пустоту: «ломаются стили», «страница недоступна».

**Фикс (уже в шаблоне):** `.ddev/nginx_full/nginx-site.conf`, в `location /`:

```nginx
location / {
    absolute_redirect off;   # Location: относительный URI ("/catalog/page-2/"), без host:port
    port_in_redirect off;    # не подставлять внутренний порт контейнера в Location
    try_files $uri $uri/ /index.php?$args;
}
```

С `absolute_redirect off` + `port_in_redirect off` редирект относительный и без
внутреннего порта — работает за любым прокси и туннелем. Обе строки **уже в
шаблоне**: `.ddev/nginx_full/nginx-site.conf` (location /). **На проде** убедись,
что они же есть в server-блоке Nginx (частая причина «на локалке работает, на
проде сломалось»).

## 2. VPN и туннели (Cloudflare/ngrok)

**Симптом:** `cloudflared`/`ngrok` не поднимает туннель, отдаёт ошибку/403/сброс
соединения; на другой машине — работает.

**Механика.** Клауд-провайдеры туннелей агрессивно борются с абьюзом:
подключения **с IP датацентров и выходов коммерческих VPN** помечаются как
рискованные — Cloudflare TryCloudflare может отклонять туннель, ngrok —
показывать interstitial/ban. VPN-туннель в дополнение к туннелю публикации —
двойная обёртка, где оба конца фильтруют друг друга.

**Правило:** туннели поднимать **без VPN**. Если VPN нужен для другой задачи
(доступ к заблокированному ресурсу) — завершить сессию VPN перед работой с
туннелем. Диагностика: `cloudflared tunnel --url http://localhost:80` с
выключенным VPN; если поднимается — дело было в IP.

**Команды туннеля** (обёртка dpx):
- `dpx ddev share --here` (провайдер — по конфигу, по умолчанию ngrok;
  `share_default_provider` в `.ddev/config.yaml`);
- cloudflared: `dpx ddev share --here --provider=cloudflared` или напрямую
  `cloudflared tunnel --url https://<slug>.ddev.site` с машины, где стоит cli.

## 3. Дублирование путей и зацикленные редиректы

**Симптом:** бесконечный 301 (`ERR_TOO_MANY_REDIRECTS`), или каждый переход
«дописывает» домен/путь: `https://tunnel.example/https://site.ru/page/`.

**Механика.** WordPress канонизирует URL по `siteurl`/`home` из БД: заходим по
туннель-адресу → WP отвечает 301 на канонический `siteurl` → Nginx (см. п.1)
добавляет слеш → снова редирект на siteurl → loop. Отдельно: относительные
редиректы Nginx при расстроенном `siteurl` складываются с кривым базовым путём.

**Лечение (по нарастающей агрессивности):**

```bash
# 1. Диагностика: какие канонические URL в БД
dpx ddev wp option get siteurl --here
dpx ddev wp option get home --here

# 2. Правка канонических URL под текущий адрес (zero-trust: только через dpx!)
dpx ddev wp search-replace 'https://old-domain.by' 'https://<slug>.ddev.site' --all-tables --precise --here

# 3. Жёсткая фиксация (перебивает БД; удобно для туннелей) — в backend/wp-config.php:
#    define( 'WP_HOME',    'https://<slug>.ddev.site' );
#    define( 'WP_SITEURL', 'https://<slug>.ddev.site' );

# 4. После смены адреса — обязательно сброс объектного кэша (Redis кеширует опции):
dpx ddev wp redis flush --here
```

Правило для туннелей: либо меняй `siteurl/home` на туннель-адрес, либо
фиксируй `WP_HOME/WP_SITEURL` в wp-config под базовый адрес и открывай туннель
только для разового показа — смешивать два «канонических» адреса в одной
сессии нельзя.
