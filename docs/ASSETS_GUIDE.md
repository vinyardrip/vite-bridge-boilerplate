# Инструкция по работе с ассетами (Cookbook)

Понятная инструкция для верстальщика и PHP-разработчика: куда кидать файлы,
что с ними делает сборка и как полученное использовать в шаблонах и в теме WordPress.

> Этот документ — про **использование**. Как плагин устроен внутри
> (нормализация SVG, классификация, префиксация) — см. корневой `README.md`.

---

## 1. Куда кидать файлы

**Все исходники ассетов кладутся в `frontend/raw/`.** Это единственный вход
image-пайплайна. Подпапки создавать можно — структура сохранится.

**Правило: просто кинь файл в `frontend/raw/` — плагин сам разберется.**
Не нужно придумывать имена с хешами, конвертировать в WebP, собирать SVG-спрайты
или следить за путями — все это делает `vite-plugin-smart-assets` на каждой сборке
(и на работающем `pnpm dev`, с авто-перезагрузкой страницы при изменении файлов).

| Вы кладете в `frontend/raw/` | Что получаете в сборке | Куда попадает |
| --- | --- | --- |
| `photo.jpg` / `.jpeg` / `.png` | оригинал + WebP + AVIF (качество 80), с ретина-парами для 2x-исходников | `assets/img/photo.<hash>.<формат>` |
| Иконка `user.svg` | инлайн-иконку или общий спрайт (плагин решает сам, см. раздел 3) | `assets/ui/…` или `assets/icons/sprite.<hash>.svg` |
| Иллюстрация `banner.svg` | оптимизированный SVG для `<img>` | `assets/img/banner.<hash>.svg` |

Весь результат складывается в общий список — **манифест** `assets-manifest.json`
в корне папки сборки (`dist/assets-manifest.json`; в WP-сборке —
`backend/wp-content/themes/my-theme/assets/assets-manifest.json`). Он генерируется
автоматически, руками его не редактируют (подробнее — FAQ в разделе 6).

Два простых правила именования:

- **Имена файлов уникальны** в пределах `frontend/raw/` — плагин ищет ассеты по имени
  без расширения, при дублях он предупредит и будет использовать первый найденный.
- **Скрытые файлы** (`.gitkeep` и т.п.) не обрабатываются.

## 2. Растровые изображения (JPG, PNG)

### Что делает плагин

Кинул `frontend/raw/photo.jpg` — на сборке получаешь целую серию в `dist/assets/img/`:

```
photo.a1b2c3d4.jpg      ← фолбэк (1x)
photo.a1b2c3d4.webp     ← WebP (1x)
photo.a1b2c3d4.avif     ← AVIF (1x) — самый легкий, поддержка есть во всех свежих браузерах
```

- `<hash>` (8 символов) вычисляется из **содержимого** файла: изменили картинку —
  поменялся хеш и имя файла (браузер не покажет старую версию из кеша).
- **Ретина:** если исходник шире 800px, он считается 2x-исходником (конвенция проекта:
  в `raw/` кладем именно 2x). Плагин добавит пару `photo.<hash>@2x.jpg|webp|avif`,
  а 1x-варианты сделает ресайзом пополам. Исходник уже 1x? Просто кладите как есть —
  пары `@2x` не будет.
- Один битый файл не роняет сборку: плагин предупредит и положит оригинал без вариантов.

### Как использовать во Frontend (Nunjucks)

Макрос **`ui.picture()`** собирает полный `<picture>`: AVIF → WebP → `<img>`-фолбэк,
retina-пары в `srcset` (1x/2x), размеры против CLS, `loading="lazy"`. Имя —
как файл в `raw/`, но без расширения:

```twig
{# для frontend/raw/hero.jpg #}
{{ ui.picture('hero', { alt: 'Кухня в готовом интерьере' }) }}

{# с классом на <img> (alt="" — для декоративных картинок) #}
{{ ui.picture('photo', { alt: '', imgClass: 'card__img' }) }}
```

`| safe` не нужен — макрос уже возвращает готовую разметку.

> Демо-картинка главной (`boiler-demo.jpg`) живет тоже в `frontend/raw/` —
> она выводится макросом `ui.picture()`. `frontend/src/assets/images/` —
> легаси-папка, новые картинки туда не кладут.

### Как использовать в Backend (WordPress PHP)

Штатные хелперы темы — `theme_picture()`, `theme_icon()` и `theme_asset_url()`
(`inc/assets-helpers.php`, подключен в `functions.php`). Они читают тот же
манифест `assets/assets-manifest.json` — файл считывается один раз за запрос
(static-кэш):

```php
<?php echo theme_picture( 'hero', array( 'alt' => 'Кухня в готовом интерьере' ) ); ?>
<?php echo theme_picture( 'photo', array( 'alt' => '', 'imgClass' => 'card__img' ) ); ?>

<?php echo theme_asset_url( 'img/hero.fbf7356d.jpg' ); // URL для og:image и т.п. ?>
```

- Результат — полный `<picture>`: AVIF → WebP → `<img>`-фолбэк, retina-пары
  в `srcset`, размеры против CLS, `loading="lazy"`.
- Ассета нет (или манифеста нет — не выполнен `pnpm build:wp`) →
  `RuntimeException` с именем ассета: страница падает с понятным сообщением,
  а не показывает «молчаливую» дыру.

Картинкам, загруженным через админку (uploads), это не нужно — их обрабатывает
`inc/helpers.php` (`my_theme_replace_img_with_picture()`, подробности в README).

## 3. SVG: иконки

### Магия — «вам не нужно об этом думать»

Плагин сам классифицирует каждый SVG (см. дерево решений в README) и сам решает,
что с ним делать:

- **Иконок мало и они легкие** (≤ 15 штук в `raw/`, суммарно ≤ 30 КБ и ≤ 15 КБ в gzip) —
  все иконки станут **инлайном**: разметка `<svg>` целиком попадает в HTML,
  без внешних файлов и лишних HTTP-запросов (файлы лежат в `assets/ui/<имя>.svg`).
- **Иконок много или они тяжелые** — плагин соберет их в **один спрайт**
  `assets/icons/sprite.<hash>.svg`, где каждая иконка — `<symbol id="имя-файла">`.
- Все `id`, классы и `@keyframes` внутри SVG автоматически префиксируются именем
  файла — иконки не конфликтуют между собой.

### Как использовать во Frontend (Nunjucks)

Макрос **`ui.icon()`** сам достает запись из манифеста и выдает готовый HTML —
какой маршрут выбрал конвейер (инлайн или спрайт), вызывающему все равно:

```twig
{{ ui.icon('phone') }}                                  {# инлайн <svg> — цвет наследуется от CSS color #}
{{ ui.icon('phone', 'contacts__icon') }}                {# с CSS-классом #}
{{ ui.icon('user', '', { 'aria-label': 'Профиль' }) }}  {# не декоративная (aria-hidden снимется) #}
```

- Иконки нет в `frontend/raw/` → **ошибка сборки** («Icon not found: …») —
  без «молчаливых» дырок в разметке.
- Размер и цвет инлайн-иконки задаются CSS (`width`/`height`, `color`).

### Как использовать в Backend (PHP)

**`theme_icon()`** — PHP-зеркало `ui.icon()`: режим берется из манифеста,
вызывающему все равно:

```php
<?php echo theme_icon( 'phone' ); ?>                                    // инлайн <svg>
<?php echo theme_icon( 'phone', 'contacts__icon' ); ?>                  // с CSS-классом
<?php echo theme_icon( 'user', '', array( 'aria-label' => 'Профиль' ) ); ?>
<?php echo theme_icon( 'demo-sprite', 'nav__icon' ); ?>                 // спрайт → <use>
```

- **Инлайн** — содержимое `assets/ui/<имя>.svg` вставляется целиком: класс
  сливается с корнем, декоративные иконки получают `aria-hidden="true"`
  `focusable="false"` (aria-label снимает скрытие), цвет наследуется от CSS `color`.
- **Спрайт** — `<svg class="…"><use href="https://…/assets/icons/sprite.<hash>.svg#<symbol>"></use></svg>`
  (URL и symbol — из манифеста).
- Иконки нет → `RuntimeException` («Icon not found: name»).

## 4. SVG: иллюстрации и анимации

### Как плагин отличает их от иконок

- **Иллюстрация** — SVG, в котором есть ссылки `url(#…)` или вставленные картинки
  `<image>`, много цветов (больше двух) или большой viewBox при двух цветах.
  Это полноценная графика, а не монохромная пиктограмма.
- **Анимация** — внутри есть `<animate*>` (SMIL), `@keyframes` или `<script>`.
  Анимации всегда идут **инлайном** (анимированный SVG в спрайте терял бы анимацию),
  остальные иллюстрации — через `<img>`.

### Как использовать

Иллюстрация попадает в `assets/img/<имя>.<hash>.svg` — и выводится тоже через
`ui.icon()`: макрос увидит в манифесте mode `img` и сам отрендерит `<img>`
(с `loading="lazy"`, `alt` и размерами из SVG):

```twig
{{ ui.icon('banner', '', { alt: 'Баннер акции' }) }}
```

Backend (PHP) — тот же `theme_icon()`: он увидит в манифесте mode `img` и
отрендерит `<img>` (путь хешированный, из манифеста):

```php
<?php echo theme_icon( 'banner', '', array( 'alt' => 'Баннер акции' ) ); ?>
```

## 5. Фоны и CSS

Фоновые картинки тоже кладем в `frontend/raw/` (JPG/PNG). Для SCSS есть миксин
**`bgset()`** — он сам выстраивает каскад `background-image`: AVIF → WebP → фолбэк
(браузер применяет последнее валидное объявление), а для Firefox добавляется
`image-set()` с подсказками форматов (легаси-хак через `@-moz-document url-prefix()`).

```scss
// В компоненте (все партиалы лежат на одной глубине в frontend/src/scss/):
@use "../abstracts" as a;

.hero {
	@include a.bgset("hero");       // имя файла в raw/ БЕЗ расширения
	@include a.cover-background();  // cover/center — как обычно
	min-height: a.rem(320);
}
```

- Миксин сам подставляет хешированные пути: в build он пишет токен
  `smart-asset:имя:формат`, который сборка заменяет на реальный путь
  (`css/app.*.css → ../assets/img/…`); в dev-сервере пути отдаются из памяти.
- Файл `frontend/src/scss/generated/_smart-assets-map.scss` — **генерируется**,
  его не редактируют и не коммитят.
- Если ассета с таким именем в `raw/` нет, Sass выдаст `@warn`, но сборку не уронит.

## 6. Частые вопросы (FAQ / Troubleshooting)

### «Я кинул иконку, но она стала черной»

Монохромные иконки собираются с `currentColor` вместо зашитого цвета — так одна
иконка перекрашивается в любой цвет. Цвет задается **CSS-свойством `color`** на
самой иконке или на родителе, а не внутри SVG:

```scss
.icon {          // инлайн-иконка
	color: var(--color-accent); // иконка станет акцентного цвета
	width: 1em;
	height: 1em;
}
```

Не задавайте `fill`/`stroke` в CSS для инлайн-иконок — CSS сильнее SVG-атрибутов
и «перебьет» даже легитимный `fill="none"` у контурных иконок.

### «Почему мой SVG не попал в спрайт?»

Плагин сворачивает все иконки в спрайт, только когда их много/они тяжелые.
Порог inline-vs-sprite (все три условия включительно):

- иконок **≤ 15 штук**,
- суммарно **≤ 30 КБ** в raw,
- **≤ 15 КБ** в gzip.

При выполнении условий все иконки инлайнятся (и попадают в `assets/ui/…`) —
это не ошибка, а оптимизация: инлайн дешевле пары-тройки маленьких файлов.
Превысили любой из порогов — иконки ушли в общий `assets/icons/sprite.<hash>.svg`.
Анимированные SVG в спрайт не попадают никогда — только инлайн.

### «Как обновить пути, если я пересобрал проект?»

Ничего обновлять не нужно: `assets-manifest.json` **генерируется автоматически**
на каждой сборке (и на каждом старте `pnpm dev`). Хеш в имени файла меняется,
только когда изменился сам файл, — значит, неизмененные картинки не сбрасывают
браузерный кеш. Единственное правило: **не хардкодить пути с хешами** в шаблонах,
SCSS и PHP — всегда брать их из манифеста (или через `bgset`, макросы
`ui.picture`/`ui.icon` и PHP-хелперы `theme_picture`/`theme_icon`,
которые делают это за вас).

### «Сборка упала с ошибкой `[svg:…]` или `Icon not found`»

SVG-конвейер строгий: битый XML, SVG без `viewBox` и без размеров или
неопознанный контент роняют сборку с понятной ошибкой, в которой указан файл.
То же с отсутствующими иконками: `ui.icon('name')` без файла
`frontend/raw/name.svg` уронит сборку, а не вставит пустой плейсхолдер.
На бэкенде то же правило: `theme_icon()`/`theme_picture()` без ассета в
манифесте (или без самого `assets-manifest.json` — забыт `pnpm build:wp`)
бросают `RuntimeException` с именем ассета.
Исправьте/пересохраните исходник — «мусорные» файлы в `raw/` не оставляют.

## 7. Проверка шрифтов (test-fonts)

Страница-инструмент для проверки загрузки веб-шрифтов: **`/pages/test-fonts.html`**.

Как открыть:

- `pnpm test:fonts` — поднимет dev-сервер и сразу откроет страницу;
- или вручную в работающем `pnpm dev`: `http://localhost:5173/pages/test-fonts.html`.

Зачем нужна: шрифты подключаются на сборке через `webfont-dl` (список семейств
и весов задан в `vite.config.ts`), а перечень для тестов лежит в
`frontend/src/data/site.json` (`site.fonts`). Страница гарантирует, что каждое
начертание реально загрузилось с сервера, а не подменилось системным шрифтом.

Как проверять: для каждого шрифта из `site.fonts` карточка показывает пару
**«Ожидание / Результат»** — слева текст с нужными `font-family`/`font-weight`
(как должно выглядеть), справа тот же текст, который JS проверяет через API
`document.fonts`:

- зеленая плашка **«Успешно»** — начертание загружено и применяется;
- красная плашка **«Ошибка»** — браузер рисует системный фолбэк (Times/Arial).
  Проверьте список семейств и весов в `webfont-dl` (`vite.config.ts`) и
  доступность Google Fonts из вашей сети.

Страница живет в `frontend/src/views/pages/test-fonts.njk`, логика проверки —
JS-модуль `font-tester`. Страница **dev-only**: она не попадает в production-сборку
(см. `DEV_ONLY_PAGES` в `vite.config.ts`), потому что в собранном виде её JS
отключен и проверка не имеет смысла.

## 8. Локальные шрифты (которых нет в Google Fonts)

Шрифты по умолчанию подключаются через `vite-plugin-webfont-dl` (список семейств
и весов — в `vite.config.ts`). Если клиенту нужен шрифт, которого **нет в Google
Fonts**, подключите его локально:

1. Положите файл шрифта в **`frontend/src/assets/fonts/`** (например,
   `MyCustomFont.woff2`; предпочтительный формат — WOFF2).
2. Откройте `frontend/src/scss/abstracts/_fonts.scss`, раскомментируйте пример
   `@font-face` и укажите имя семейства и файла.
3. Готово — файл автоматически попадает в сборку с хешем в имени
   (`dist/assets/fonts/MyCustomFont.<hash>.woff2`), а CSS получает
   относительную ссылку на него. В WP-сборке файл ляжет плоско в
   `assets/fonts/` темы.

Дальше шрифт используется как обычное семейство в CSS
(`font-family: 'MyCustomFont'`). Проверить, что шрифт реально загрузился,
можно на странице `/test-fonts` (раздел 7): добавьте семейство в `site.fonts`
(`frontend/src/data/site.json`).

**Важно про путь в `url()`:** `_fonts.scss` лежит в `scss/abstracts/`, поэтому
до `frontend/src/assets/fonts/` — два уровня вверх: `../../assets/fonts/`.
Не копируйте пути из чужих примеров с одним `../` — Vite не сможет
резолвнуть такой `url()` и молча оставит его в CSS «как есть» (файл не
попадет в сборку).

- Google-шрифты дублировать в `_fonts.scss` не нужно — их подключает `webfont-dl`.
- Не храните «мёртвые» файлы: всё, на что есть `@font-face`, попадает в
  production-сборку, даже если семейство нигде не используется.

## 9. Деплой на слабый хостинг (без AVIF)

Многие шаред-хостинги не умеют отдавать AVIF. Для **статического** деплоя:

1. `pnpm build:prod` — финальная сборка в `dist/` (с AVIF и **встроенным
   Critical CSS**; она остается локальной — для preview и тестов). Обычный
   `pnpm build` тоже можно, но тогда Critical CSS не встроится (он в сборку
   не входит — см. ниже).
2. `pnpm strip-avif:dist` — скрипт создаст **копию `dist-wp/`**: из HTML/CSS
   вырезаны все `<source type="image/avif">` и `image-set()`-каскады с `.avif`,
   файлы `*.avif` удалены, манифесты почищены; **WebP-источники и фолбэки
   (JPG/PNG) остались на месте**.
3. На сервер заливайте именно папку **`dist-wp/`** — оригинальный `dist/`
   скрипт не трогает. Каждый запуск пересобирает `dist-wp/` с нуля из
   текущего `dist/`, так что после правок просто повторите шаги 1–2.

**Кратко: для локальной разработки и DDEV используйте `dist/`, для заливки
на слабый хостинг — `dist-wp/`.**

**Critical CSS** (`scripts/make-critical.ts`, шаг 1 делает его за вас):
для каждой страницы в `dist/` вычисляется критический CSS (вьюпорты
1300×900 и 414×896) и инлайнится в `<head>`; основной `<link rel="stylesheet">`
превращается в `rel="preload"`, а рабочий линк добавляется в `<body>` — стили
грузятся даже с отключенным JavaScript. Он есть только в `pnpm build:prod`
(`pnpm build` + `make-critical`): генерация через Puppeteer добавляет ~15 с,
поэтому обычная сборка для локальных проверок его не запускает. В `build:wp`
Critical CSS нет намеренно — WP-сборка не строит HTML, разметку рендерит PHP.

Скрипт проверяет результат: если в html/css/манифестах остались файловые
ссылки на `.avif`, он перечислит их с файлами и строками и упадет с ошибкой —
деплоить нельзя.

Для **WordPress-темы** (PHP-деплой) есть свой вариант: цепочка
`pnpm build && pnpm sync:theme && pnpm build:wp-strip-avif` (режет тему
in place) — подробности в корневом `README.md`, раздел
«Деплой на шаред-хостинг».

## 10. Favicons и PWA-иконки

**Исходник фавиконки лежит в `frontend/public/favicon.svg`.** Сгенерированные
файлы попадают в `dist/assets/favicons/` и синхронизируются в WP. Не кидайте
готовые фавиконки вручную — используйте генератор.

Как это работает:

1. Правите исходник `frontend/public/favicon.svg` (логотип дизайнера).
2. Запускаете `pnpm favicons:generate` (или любую сборку — она делает это
   автоматически). Генератор `@vite-pwa/assets-generator` (пресет
   `minimal-2023`) пишет в `frontend/public/assets/favicons/`:

   | Файл | Что это |
   | --- | --- |
   | `favicon.svg` | копия исходника (SVG-фавиконка для современных браузеров) |
   | `favicon.ico` | классический ICO 48×48 (IE/старые браузеры) |
   | `pwa-64x64.png`, `pwa-192x192.png`, `pwa-512x512.png` | PNG-иконки (manifest/PWA) |
   | `maskable-icon-512x512.png` | иконка с безопасной зоной (Android adaptive) |
   | `apple-touch-icon-180x180.png` | иконка для iOS/закладок Safari |

3. `public/` копируется в сборку как есть → файлы оказываются в
   `dist/assets/favicons/`, а после `pnpm sync:theme` — в
   `assets/assets/favicons/` темы WordPress (двойной `assets/` — след
   структуры `dist/`, не опечатка).

Теги `<link>` уже вписаны в шаблоны — руками их добавлять не нужно:

- фронтенд: `frontend/src/views/layouts/_default.njk` (`<head>`);
- WordPress: `backend/wp-content/themes/my-theme/header.php`.

Сгенерированные файлы — **артефакты**: они коммитятся (генерация
детерминирована, пересборка не «грязнит» git), но их не редактируют и не
добавляют вручную — только через генератор из исходника.

> Нюанс: исходник и вывод разнесены скриптом `scripts/make-favicons.ts` —
> CLI генератора умеет писать только в папку исходной картинки, поэтому
> используется его программный API. Если когда-нибудь понадобится сменить
> пресет/набор иконок — править его (см. докблок).

## Куда не нужно ничего класть

- **favicon и PWA-иконки** — исходник: `frontend/public/favicon.svg`
  (генерация `pnpm favicons:generate`, вывод — `frontend/public/assets/favicons/`;
  см. раздел 10);
- **шрифты** — Google-шрифты подключаются через `webfont-dl` (файлы в `raw/`
  не кладут); шрифты, которых нет в Google, — через
  `frontend/src/assets/fonts/` + `abstracts/_fonts.scss` (см. раздел 8);
- **картинки из админки** — загружаются в uploads, их обработка — `inc/helpers.php`.
